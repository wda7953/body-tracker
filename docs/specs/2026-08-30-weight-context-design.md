# 今日體重情境（成因判斷）設計

**日期**：2026-08-30
**狀態**：設計已確認，待寫實作計畫
**目標**：體重上升時，用「已經在撈的 Garmin 恢復訊號 + 生理期」判斷這次是水腫／沒睡飽／訓練發炎／還是真的變胖，貼在儀表板每天顯示。

---

## 背景與動機

減脂追蹤最大的干擾是「單日體重是雜訊」——一天可以差 1–2kg，多半是水和消化道內容物，不是脂肪。使用者原本問「還要加什麼數據才能判斷成因」，但盤點後發現：

- **撈取端（`scripts/garmin_daily.py`）已經全部撈進來了**：`resting_hr`、`hrv_last_night`、`hrv_status`、`sleep_score`、`sleep_hours`、`avg_stress`、`body_battery`、`active_kcal`、`training_readiness`。
- 儀表板也已顯示這些原始數字（今日訓練準備、昨晚 HRV、近3日恢復狀態）。
- **缺的不是數據，是判斷邏輯**：`advice.js` 只用 sleep/stress/battery 給一句籠統建議，沒把「體重那天的變化」跟恢復訊號綁在一起，也完全沒用到已撈的 HRV / RHR。

已於本機截圖確認使用者錶款實際有回傳 HRV（昨晚 82ms、狀態均衡），恢復訊號齊全可用。

**手動輸入一律不做**（會懶得記、記了也不齊，反而汙染趨勢判讀）。全部用已自動撈取的數據。

## 功能規格

### 觸發與位置
- 儀表板頂部新增一塊常駐卡片「今日體重情境」，**每天都顯示**（不是只在體重高時才出現）。
- 只動前端顯示，**不動撈取端、不動後端 GAS、不動 LINE 通知**。

### 比較基準
同時顯示兩個數字：
- **比昨天**：今日體重 − 昨日體重
- **比 7 日均線**：今日體重 − 近 7 日移動平均

**成因標籤的判斷錨定「比 7 日均線」那個**（過濾單日雜訊）；比昨天只當補充情境顯示。

### 成因判斷門檻
今日體重 **高於 7 日均線 > +0.2kg** 才進入成因判斷。門檻設為可調常數。

### 五類成因標籤（同一天可同時中多個，全部列出）

| 標籤 | 觸發條件 | detail 內容 |
|---|---|---|
| 🌙 恢復不足型水腫 | HRV 狀態非「均衡」**或** RHR 高於個人近14天基準 +3bpm **或** 睡眠分 < 60 **或** 壓力 > 50 **或** 電量 < 40 | 標出實際中的是哪幾項（例：「睡眠分52、HRV偏低」） |
| 🩸 荷爾蒙型水腫 | 今日落在生理期內，或落在預測經期前 ~7 天（黃體期） | 標出是經期中還是黃體期 |
| 💪 訓練發炎型 | 前一天 `active_kcal` 落在近 14 天的前 20%（≥ 80 百分位） | 「昨天活動量偏高，肌肉修復儲水」 |
| 📈 可能真的變胖 | 以上都沒中 **且** 7 日均線本身也在往上 | 提醒注意攝食 |
| ✅ 正常波動（鎖水） | 高一點但恢復訊號全正常、均線沒上升 | 免緊張，純鎖水 |

### 體重未高於均線時
- 均線在下降 → ✅「均線下降中、恢復良好，節奏很好」
- 均線平穩 → 「數據平穩，照常執行」

### 面板呈現範例（某天中兩個成因）
```
┌─ 今日體重情境 ───────────────────────┐
│  比昨天 +0.8kg   ·   比7日均線 +0.4kg  │
│                                        │
│  🩸 生理期(黃體期)→ 荷爾蒙自然儲水    │
│  🌙 沒睡飽(睡眠分52、HRV偏低)→ 儲水  │
│                                        │
│  → 兩個都在推高,多半是水不是脂肪,    │
│     維持節奏,3–5 天後再看均線。        │
└────────────────────────────────────────┘
```
末尾一句彙整建議：多個水腫成因 → 「多半是水不是脂肪，維持節奏」；可能真胖 → 「留意攝食」；正常 → 對應鼓勵語。

## 技術架構

### 新增純函式檔 `js/context.js`
零外部相依，與 `js/calc.js` 同風格（結尾同時 `module.exports` 與 `window.Context`），`node --test` 可測。

對外主函式：
```
weightContext(input) -> {
  deltaVsYesterday,   // number | null
  deltaVsTrend,       // number | null
  trendRising,        // bool | null（7日均線本身方向）
  causes: [{ icon, label, detail }],  // 命中的成因，可 0..n 個
  verdict             // 彙整建議字串
}
```

**輸入**：
- 近期每日資料陣列（已含 weight / resting_hr / hrv_last_night / hrv_status / sleep_score / avg_stress / body_battery / active_kcal），依日期
- 生理期開始日字串陣列
- 設定：門檻（預設 +0.2）、RHR 基準加幅（預設 +3）、各項閾值

### 判斷邏輯（全放 `context.js`，含基準計算）
- **7日均線 / trend 方向**：複用 `calc.movingAverage`、`calc.weeklyTrendChange`
- **RHR 基準**：近 14 天 `resting_hr` 平均；**需 ≥ 5 天有效資料才啟用**此條，否則跳過
- **active_kcal 前 20%**：近 14 天百分位；**需 ≥ 10 天有效資料才啟用**，否則跳過訓練發炎判斷
- **HRV 狀態對應**：`BALANCED` → 正常；`LOW` / `UNBALANCED` / `POOR` → 不良；`null` / `NONE` → 未知，跳過此條
- **生理期**：複用 `calc.cycleStats`；黃體期定義 = 預測經期前 7 天內

### 資料缺失處理原則
任一訊號為空就跳過對應規則，**不誤判**。所有比較在資料不足時回傳 null / 略過，不靜默算出 NaN。

### UI（`index.html`）
儀表板頂部加卡片容器，載入後呼叫 `Context.weightContext(...)`，把結果渲染成上述面板。沿用現有深色系樣式。

## 測試（延續現有 `node --test`，`tests/context.test.js`）
- 各單一成因各一案（恢復不足 / 荷爾蒙 / 訓練發炎 / 可能真胖 / 正常波動）
- 多重成因疊加（生理期 + 沒睡飽 同時命中，兩個都列出）
- 體重未高於均線：均線下降 / 均線平穩 兩案
- 資料不足：RHR < 5 天、active_kcal < 10 天時對應規則正確跳過（不誤判）
- HRV status 各值對應正確；null/NONE 跳過
- 邊界：剛好 +0.2kg 門檻的臨界行為

## 不做（YAGNI）
- 不加任何手動輸入
- 不改 Garmin 撈取端、不改後端 GAS、不動 LINE 通知
- 不接 LLM 潤飾（規則式即可，可解釋、零成本）
- 訓練發炎型先用 active_kcal 統計基準試用；active_kcal 分不出重訓與走路，是已知弱點，試用一段時間後再決定調整、換 Garmin 訓練負荷指標、或移除。
